# План: играбельные табы, re-fingering, перегенерация из UI и печать на A4

> План рассчитан на самостоятельную реализацию LLM-агентом. Прочти его целиком
> до первой правки. Затем прочти `AGENTS.md` и `LESSONS.md` — это обязательные
> правила проекта. Если что-то в плане противоречит реальному коду — верь коду,
> зафиксируй расхождение в PR-описании и выбери минимально инвазивное решение.

## 0. Контекст и цель

Пользователь пишет музыку (Suno → дорисовка в Guitar Pro 8), конвертирует её
этим проектом в MIDI для Kontakt/Shreddage, а теперь хочет **переиграть партии
вживую** (гитара — Les Paul, бас). Проблема: партии в GP нарисованы «по нотам»
или плохо распознаны — аппликатура нечеловеческая, играть невозможно.

Нужно добавить в проект **аддитивный** пайплайн «playable tabs»:

1. Для каждого трека типа **GUITAR или BASS** (соло, ритм, чистая акустика,
   бас — всё семейство; барабаны/синты/струнные НЕ участвуют) строится
   **чистый score-MIDI** (без keyswitch-нот, pitch bend, CC и humanize).
2. Он прогоняется через **два независимых оптимизатора аппликатуры**:
   - **gtrsnipe** (https://github.com/scottvr/gtrsnipe) — скоринг растяжки,
     позиции, sweet-spot; выдаёт ASCII-таб + по-нотное (струна, лад) + техники;
   - **tuttut** (https://github.com/natecdr/tuttut) — HMM + Витерби; ASCII-таб.
3. Результаты (два ASCII-таба + score-MIDI) скачиваются со страницы джоба.
4. (Фаза 2) Из маппинга gtrsnipe генерируется **пропатченная копия исходного
   .gp файла** с новой аппликатурой (те же ноты, те же длительности, другие
   струны/лады) — пользователь открывает её в Guitar Pro 8 рядом с оригиналом.
5. (Фаза 3) Пользователь может **изменить параметры на странице джоба и
   перегенерировать** табы конкретного трека без повторной загрузки файла.
6. (Фаза 4) Любой таб можно **напечатать на A4 прямо с бэкенда**: сервер
   рендерит PDF и отправляет его в CUPS (`lp`). Принтер — HP LaserJet 1102
   (моно-лазер) на CUPS-сервере **192.168.20.64**. Имя очереди на момент
   написания плана неизвестно — выясняется на этапе реализации (§7.2).

Зафиксированные решения (НЕ пересматривать):

- Гитара: **стандартный EADGBE** (E2=40, A2=45, D3=50, G3=55, B3=59, E4=64),
  6 струн, **22 лада** (Les Paul). Бас: **стандартный EADG**
  (E1=28, A1=33, D2=38, G2=43), 4 струны, 20 ладов. Дроп-строёв нет.
- Использование некоммерческое. Лицензия gtrsnipe (PolyForm Noncommercial
  1.0.0) это разрешает, включая вендоринг с изменениями — при сохранении
  текста лицензии и Required Notices.
- Внедряются ОБА тула — пользователь хочет сравнить результаты.
- Всё новое — opt-in (чекбокс/флаг), по умолчанию поведение проекта
  байт-в-байт не меняется.
- Печать с бэкенда явно запрошена пользователем (не требовать подтверждений
  в рантайме; кнопка «Печать» на UI и есть подтверждение).

## 1. Жёсткие правила (нарушение = провал задачи)

1. **Не менять музыкальное поведение конвертера.** Ни одной правки логики в
   `build_instrument_midi`, `build_other_midi`, `build_drum_midi`, эмиссии
   KS/PB/CC, humanize, тайминга. Новый код только читает существующие функции.
2. **Не редактировать** `config/articulation_maps/*` и
   `config/humanize_profiles/*`.
3. Существующие выходные файлы джоба (per-track `.mid`, `_ALL.mid`, zip) при
   выключенной опции должны остаться **байт-в-байт** прежними. При включённой —
   прежние файлы не меняются, добавляются только новые.
4. Перед заявлением «готово» — реальный прогон на настоящем `.gp` файле
   (см. §9) и просмотр результата глазами.
5. Сетевой доступ в рантайме — только к CUPS-серверу из настроек печати.
   Всё остальное ставится на этапе установки зависимостей / вендорится.
6. Эндпоинты, принимающие имена файлов (`regen`, `print`), обязаны проверять
   имя по списку артефактов из манифеста джоба, а не по файловой системе —
   никакого path traversal.

## 4. Фаза 1 — score-MIDI + два ASCII-таба

### 4.1 Отбор треков и построение чистых score-событий

**Какие треки:** `resolve_track_type(track)` (`gp_to_shreddage.py:122`)
возвращает тип; в пайплайн идут **GUITAR и BASS** (проверь точные значения-
строки, которые возвращает функция). На образце пользователя (§9) это
`Solo Guitar`, `Rhytm Guitar` (опечатка в файле), `Steel Guitar`,
`Electric Bass`. DRUMS/OTHER не участвуют.

**Почему нельзя брать готовые `.mid` из конвертера:** в них keyswitch-ноты в
суб-контр-октаве, pitch-bend кривые, CC1/CC11, humanize-сдвиги и
легато-перекрытия 40 мс. Любой табулятор сделает из этого мусор (KS-ноты
станут «нотами»). Источник данных — распарсенная песня.

В `playable_tabs.py`:

```python
from gp_import import parse_song
from gp_to_shreddage import (
    resolve_track_type, iter_voice_beats_with_canonical_ticks,
    duration_ticks, TICKS_PER_BEAT, safe_filename,
)
from guitarpro.models import NoteType
```

`build_score_events(track) -> list[ScoreNote]` где
`ScoreNote = (start_tick, dur_ticks, pitch, velocity)`:

- Итерация битов: `iter_voice_beats_with_canonical_ticks(track)` — она уже
  отдаёт канонические `beat_tick`/`dur` (tpb=960, первый такт с тика 0) и
  обходит все голоса. Логика описана в `gp_to_shreddage.py:297`.
- Питч обычной ноты: `string_pitch = {s.number: s.value for s in track.strings}`,
  `pitch = string_pitch[note.string] + note.value` — ровно как в
  `build_instrument_midi` (`gp_to_shreddage.py:790`). Флажолеты передаём по
  fretted-питчу (той же формулой), потому что для игры руками важна ПОЗИЦИЯ,
  а не звучащая высота. Пометь это в докстринге.
- **Лиги:** нота с `note.type == NoteType.tie` не создаёт новой атаки, а
  продлевает предыдущую ноту той же струны — повтори семантику из
  `gp_to_shreddage.py:798-...` (найди блок «tie-нота: продлеваем предыдущую»).
  Реализуй через словарь `last_note_on_string[string] -> index в списке` и
  увеличение `dur_ticks` у уже добавленной ноты.
- Мёртвые ноты (dead/x) и грейс-ноты включай как обычные ноты с их питчем —
  для аппликатуры они полноценные позиции левой руки.
- Паузы/пустые биты просто пропускаются (тик двигает итератор).
- НИКАКОГО humanize, KS, PB, CC — только note on/off.

`write_score_midi(events, out_path, song)` — Type 0, tpb=960, один трек:
темп-события из песни (первый темп достаточен; если в
`song.tempo_automations`/mixTableChange есть смены — добавь их как `set_tempo`
по тем же тикам, посмотри, как это делает `build_instrument_midi` около
`gp_to_shreddage.py:752`), time signature из заголовков тактов, затем
note_on/note_off. Использовать `mido` (уже в зависимостях).

### 4.2 Адаптер gtrsnipe

НЕ использовать их MIDI-ридер. Строить их структуры напрямую
(`third_party/gtrsnipe_core/core/types.py`):

```python
MusicalEvent(time=start_tick / 960, pitch=pitch,
             duration=dur_ticks / 960, velocity=velocity)
```

(время и длительность у них в ДОЛЯХ-четвертях, float).

Вызов: `GuitarMapper(config).map_events_to_fretboard(events,
no_articulations=False)` → те же события с заполненными `string`, `fret`,
`technique` (сохрани результат — он нужен Фазе 2). Затем собрать их `Song` с
одним `Track` и отдать в `AsciiTabGenerator.generate(song, command_line=...)`;
в `command_line` передай строку с именем пресета и датой — она печатается в
шапке таба. `max_line_width` подбери под A4-печать (§7.1): ~100 символов.

Пресеты (константы в начале `playable_tabs.py`; значения — стартовая точка,
подлежат подгонке пользователем через UI Фазы 3):

```python
GUITAR_BASE = dict(tuning="STANDARD", num_strings=6, max_fret=22, capo=0,
                   unplayable_fret_span=4)
PRESET_SOLO = MapperConfig(**GUITAR_BASE, sweet_spot_low=5, sweet_spot_high=15,
                           sweet_spot_bonus=1.0, movement_penalty=5.0,
                           string_switch_penalty=8.0)
PRESET_RHYTHM = MapperConfig(**GUITAR_BASE, sweet_spot_low=0, sweet_spot_high=7,
                             sweet_spot_bonus=1.0, prefer_open=True)
PRESET_BASS = MapperConfig(tuning="BASS_STANDARD", num_strings=4, max_fret=20,
                           capo=0, unplayable_fret_span=5,
                           sweet_spot_low=0, sweet_spot_high=12,
                           sweet_spot_bonus=1.0, prefer_open=True)
```

Автовыбор пресета: тип BASS → `bass`; имя трека содержит `solo`
(без регистра) → `solo`; иначе `rhythm`.

### 4.3 Адаптер tuttut

tuttut принимает `pretty_midi.PrettyMIDI`, поэтому путь простой: записать
`<track>.score.mid` (см. 4.1), затем:

```python
import pretty_midi
from tuttut.logic.tab import Tab
from tuttut.logic.theory import Tuning

TUNING_GUITAR = Tuning()                                  # EADGBE
TUNING_BASS = Tuning(["G2", "D2", "A1", "E1"])            # стандартный бас

pm = pretty_midi.PrettyMIDI(str(score_mid_path))
tab = Tab(track_basename, tuning, pm,
          weights={"b": 1, "height": 1, "length": 1, "n_changed_strings": 1},
          output_dir=str(out_dir))
tab.to_ascii()   # пишет <track_basename>.txt в out_dir
```

Файл после генерации переименуй в `<track>.playable.tuttut.txt`.

Известное свойство tuttut: на сложных файлах может падать (сам автор
предупреждает). Каждый тул оборачивается в свой `try/except Exception`:
падение одного тула — WARN в summary трека и отсутствие его файла, но джоб
живёт, второй тул и весь остальной экспорт не страдают.

### 4.4 Именование выходов (в каталоге output джоба)

- `<track>.score.mid` — чистый score-MIDI (полезен и сам по себе);
- `<track>.playable.gtrsnipe.txt`;
- `<track>.playable.tuttut.txt`.

`<track>` — через `safe_filename`, как у остальных артефактов. PDF-версии
(`.pdf` вместо `.txt`) добавляет Фаза 4.

### 4.5 Интеграция в web UI (`app.py`)

По образцу существующей опции `humanize` (см. `upload()` ~`app.py:610`,
`create_job` ~`app.py:536`, манифест, бейджи на странице джоба):

1. Чекбокс `playable_tabs` в форме `/upload` (off по умолчанию), подпись
   вида «Играбельные табы для гитары и баса (эксперимент)».
2. В `create_job`: если флаг взведён — после основной конвертации выполнить
   пайплайн 4.1–4.3 для каждого GUITAR/BASS-трека.
3. В манифест джоба: `"playable_tabs": true/false` и на каждый участвующий
   трек — объект `playable`:
   ```json
   {"preset": "solo", "params": {…фактические значения…},
    "files": ["<track>.score.mid", "<track>.playable.gtrsnipe.txt", …],
    "status": {"gtrsnipe": "ok", "tuttut": "failed: <кратко>"},
    "version": 1}
   ```
   `params` хранит ПОЛНЫЙ действующий набор регулируемых параметров (см. §6) —
   он же префилл формы перегенерации.
4. На странице джоба у трека — ссылки на файлы (реиспользуй роут
   `download_track`; к ссылкам добавляй `?v=<version>` для сброса кеша
   браузера после перегенерации) и бейдж пресета. Ошибка тула — WARN-текст.
5. Zip-архив (`make_zip`) собирает каталог output целиком — убедись, что новые
   файлы попали в него автоматически, и не сломай это.

### 4.7 Приёмка Фазы 1

  если были — они остаются (не транспонируем молча), но попадают в отчёт
  (§5.1 п.6).
- Число атак (note-on) в score-MIDI == числу не-tie нот трека в GP (сравни
  напрямую по `parse_song`). Это главный тест на правильность обработки лиг.
- С выключенным чекбоксом джоб байт-в-байт как раньше (сравни выходной каталог
  двух прогонов `diff -r`).

## 5. Фаза 2 — re-fingering исходного .gp

Идея: НЕ строить GP-файл с нуля (квантизация ритма в GP-длительности — болото),
а **пропатчить копию исходного файла**, заменив только струну/лад у нот
GUITAR/BASS-треков на результат маппера gtrsnipe. Ритм, такты, темпы, динамика,
нотный стан не меняются вообще; питч каждой ноты сохраняется по построению
(`open_pitch[новая струна] + новый лад == старый питч`).

### 5.1 Для входа `.gp` (GP7/GP8 zip-архив) — основной случай пользователя

Инфраструктура уже есть в `gp_import.py`:

- чтение/запись архива: `_write_patched_gp` (`gp_import.py:350`) — копирует
  архив, подменяя `Content/score.gpif`;
- обход GPIF: `_extract_gpif_note_extras_root` (`gp_import.py:387`) уже
  разыменовывает цепочку MasterBars → Bars → Voices → Beats → Notes. **Прочти
  её целиком** и напиши по её образу обход
  `iter_gpif_notes(root, track_idx) -> yield (note_element, порядковый номер)`
  в документном порядке битов.

Порядок работы `refinger_gp(src_path, mappings) -> Path`:

1. Распаковать `Content/score.gpif`, `ET.fromstring`.
2. Для каждого GUITAR/BASS-трека: найти его в GPIF по имени
   (`Tracks/Track/Name`). ВАЖНО: `parse_song` для мультистафф-треков работает
   с уже РАСШИРЕННЫМ временным файлом (`_expand_multistaff_tracks`), поэтому
   индексы могут не совпадать с оригиналом. Гитарные треки одностаффные, но
   сопоставляй по имени, а не по индексу, и если трек в GPIF содержит >1
   staff — пропусти его с WARN (re-fingering для него не делаем).
3. **Шаг-исследование (сделай до написания патчера):** выясни конвенцию
   нумерации струн в GPIF эмпирически. Возьми образец (§9), выведи для первых
   5 нот гитарного трека пары (GPIF `Property name="String"` / `name="Fret"`)
   и сравни с тем, что отдал `parse_song` для тех же нот (`note.string`,
   `note.value`, `realValue`). Из сравнения выведи формулу пересчёта
   `apollotab_string <-> gpif_string` (ожидаемо: в GPIF String 0 = самая
   низкая струна, у ApolloTab string 1 = самая высокая, но НЕ доверяй этому
   утверждению — проверь). Помни, что gtrsnipe `FretPosition.string` 0 = самая
   высокая струна — итого в игре ТРИ конвенции нумерации; сведи их в одну
   таблицу-комментарий рядом с формулами пересчёта. Для баса всё то же с
   4 струнами.
4. Пройди ноты GPIF-трека и результат `map_events_to_fretboard` синхронно,
   **в одном и том же порядке обхода** (тот же порядок битов, что у
   `iter_voice_beats_with_canonical_ticks`). Tie-ноты в GPIF тоже несут
   String/Fret — им проставляется та же позиция, что у их атаки (для этого
   при построении score-событий сохрани для каждой атаки список «хвостовых»
   tie-нот, либо веди отдельный параллельный список всех нот с флагом tie).
5. Для каждой ноты: `new_fret = old_pitch - open_pitch[new_string]`;
   `assert 0 <= new_fret <= max_fret`; записать оба Property. Ничего больше в
   элементе ноты не трогать (бенды, вибрато, пальцы правой руки — остаются).
6. Ноты, для которых маппер не нашёл позицию, или питч вне диапазона строя —
   НЕ менять, добавить строку в `<track>.unplayable_report.txt`
   (такт, доля, питч, причина). Автотранспонирование запрещено.
7. Сериализовать XML, `_write_patched_gp`, переложить результат в output джоба
   как `<base>_refingered.gp`.

### 5.2 Обязательная пост-верификация (сильный инвариант)

Сразу после записи прогнать `parse_song(patched_path)` и сравнить с
`parse_song(src_path)`:

- по каждому треку последовательность `(start_tick, dur, realValue/pitch)`
  всех нот **идентична** (питчи и ритм не изменились);
- на GUITAR/BASS-треках последовательность `(string, value)` совпадает с тем,
  что назначил маппер (с учётом формулы пересчёта нумерации).

Любое расхождение → пропатченный файл удаляется, в summary WARN
«re-fingering отменён: питч-инвариант нарушен (<деталь>)». Это защита от
ошибки в конвенции струн или в порядке обхода — молча портить партитуру
запрещено.

### 5.3 Для входа `.gp5` (бонус, делать после того как 5.1 работает)

`pyguitarpro` (уже в зависимостях) читает и пишет gp5:
`song = guitarpro.parse(path)`; у нот менять `note.string` (1 = верхняя
струна) и `note.value` (лад), сохраняя `realValue`; `guitarpro.write(song,
out_path)`. Та же пост-верификация 5.2 (парсить обратно и сравнивать). Если
входной формат не `.gp` и не `.gp5` — re-fingering просто пропускается с INFO.

### 5.4 Приёмка Фазы 2

- На образце (§9) создаётся `<base>_refingered.gp`, пост-верификация 5.2
  зелёная, гитарные И басовый треки перефингерены.
- `unplayable_report.txt` либо пуст, либо перечисляет конкретные ноты.
- Пользователь открывает файл в GP8 (ручной шаг — попроси его в PR-описании
  проверить): нотный стан идентичен оригиналу, табулатурная строка изменилась,
  партии стали лежать в позициях.

## 6. Фаза 3 — перегенерация трека с параметрами из UI

Цель: пользователь меняет пресет/веса на странице джоба и получает новые табы
конкретного трека, не загружая файл заново.

### 6.1 Регулируемые параметры (единый источник истины)

Константа `TUNABLE_PARAMS` в `playable_tabs.py` — словарь
`имя -> (тип, мин, макс, дефолт, подпись для UI)`. Whitelist, по которому
строится и форма, и серверная валидация (НИКАКОГО `setattr` по произвольным
ключам из формы):

| параметр | тип | диапазон | на что влияет |
|---|---|---|---|
| `preset` | enum | auto/solo/rhythm/bass | база всех остальных |
| `sweet_spot_low` | int | 0..22 | нижняя граница рабочей зоны |
| `sweet_spot_high` | int | 0..22, > low | верхняя граница рабочей зоны |
| `sweet_spot_bonus` | float | 0..10 | сила притяжения к зоне |
| `movement_penalty` | float | 0..50 | штраф прыжков по грифу |
| `string_switch_penalty` | float | 0..50 | штраф смены струн |
| `unplayable_fret_span` | int | 3..6 | предел растяжки |
| `prefer_open` | bool | — | предпочитать открытые струны |

Порядок применения: пресет → поверх него явно переданные поля. Полный
действующий набор пишется в `manifest.playable.params` (§4.5 п.3).

tuttut-веса (`b`, `height`, `length`, `n_changed_strings`) в v1 НЕ выносить в
UI — оставить дефолт; вынести их — отдельная задача Фазы 5, если пользователь
попросит.

### 6.2 Эндпоинт

`POST /jobs/<job_id>/playable/regen`, поля формы: `track` (basename трека из
манифеста) + параметры из §6.1.

Сервер:
1. Джоб существует, `playable_tabs` включён, `track` есть в манифесте —
   иначе 404/400.
2. Валидация параметров строго по `TUNABLE_PARAMS` (тип, диапазон,
   `high > low`); ошибка → 400 с текстом, ничего не перегенерировано.
3. Перепарсить исходник из `input/` каталога джоба (путь берётся из
   манифеста), взять нужный трек.
4. Перегенерировать ТОЛЬКО артефакты этого трека: gtrsnipe-таб (+ его PDF,
   если Фаза 4 уже сделана), tuttut-таб (+ PDF), unplayable-report.
   `<track>.score.mid` от параметров НЕ зависит — не перегенерировать
   (только если файл отсутствует).
5. `<base>_refingered.gp` зависит от ВСЕХ треков: перестроить его целиком,
   прогнав маппер для каждого участвующего трека с ЕГО сохранёнными в
   манифесте параметрами (для регенерируемого — с новыми). Пост-верификация
   5.2 обязательна и здесь.
6. Обновить в манифесте `params`, `status`, `version += 1`; redirect на
   страницу джоба (обычная форма, без AJAX — проект без JS-фреймворков,
   и существующий UI работает так же).

Генерация одного трека занимает секунды — синхронный запрос допустим, никаких
фоновых очередей не городить.

### 6.3 UI

На странице джоба у каждого участвующего трека — свёрнутый блок
«Параметры аппликатуры» (`<details>`): селект пресета + числовые поля из
§6.1, префилл из `manifest.playable.params`, кнопка «Перегенерировать».
Рядом бейдж `v<version>` и время последней генерации. Стили — в духе
существующего светлого UI.

### 6.4 Приёмка Фазы 3

- Смена `sweet_spot_low/high` у «Solo Guitar» на образце (§9) меняет
  содержимое gtrsnipe-таба (проверь diff), version растёт, ссылки отдают
  свежие файлы, остальные треки не тронуты (mtime их файлов не изменился).
- Невалидные параметры (`high <= low`, отрицательный штраф, чужое имя поля)
  → 400, файлы не изменены.
- `_refingered.gp` после регена проходит пост-верификацию 5.2.

## 7. Фаза 4 — печать на A4 через CUPS

### 7.1 PDF-рендер (`tab_print.py :: ascii_to_pdf`)

Вход: путь к `.txt` табу + заголовок. Выход: PDF рядом, то же имя с `.pdf`.

- fpdf2, A4 портрет, поля 12 мм, шрифт `static/fonts/DejaVuSansMono.ttf`
  (вендорить в репо — см. §3.3), стартовый кегль 8.5pt.
- Табулатурные строки НЕ переносить (перенос ломает таб). Если самая длинная
  строка не влезает в ширину — уменьшать кегль до влезания, нижний предел
  6pt; если и при 6pt не влезает — WARN в статус и рендер с обрезкой по
  правому краю (честно указать это в колонтитуле страницы).
- Разрыв страницы — только между «системами» таба (блок из 6 строк для
  гитары / 4 для баса + пустая строка-разделитель), не внутри системы.
  Парси системы по пустым строкам.
- Колонтитул: название трека, пресет, `v<version>`, дата, номер страницы.
- Для gtrsnipe подбери `max_line_width` при генерации ASCII (§4.2) так, чтобы
  при 8.5pt строка гарантированно влезала (~100 символов); для tuttut ширину
  не контролируем — работает shrink-to-fit.

PDF генерируется вместе с табами (в `create_job` и в regen) — файлы
`<track>.playable.gtrsnipe.pdf`, `<track>.playable.tuttut.pdf` появляются в
output, манифесте и zip как обычные артефакты (их можно скачать и напечатать
локально, если серверная печать недоступна).

### 7.2 Отправка в CUPS (`tab_print.py :: print_pdf`)

- Конфиг: env `CUPS_SERVER` (уже известен: `192.168.20.64`) и `CUPS_PRINTER`
  (имя очереди). **Первый шаг реализации:** выяснить имя очереди командой
  `lpstat -h 192.168.20.64 -a` (список принимающих очередей; ожидается
  что-то вроде `HP_LaserJet_Professional_P1102`). Если команда недоступна/
  очередей несколько — СПРОСИТЬ пользователя, не угадывать. Вписать имя в
  `docker-compose.yml` (env) и в `.env.example`-подобный комментарий.
- Отправка: `subprocess.run(["lp", "-h", CUPS_SERVER, "-d", CUPS_PRINTER,
  "-o", "media=A4", "-o", "sides=one-sided", str(pdf_path)],
  timeout=15, capture_output=True)`. Успех — распарсить `request id is ...`
  из stdout и показать его пользователю. Ошибка/таймаут — flash-сообщение
  WARN с stderr, БЕЗ ретраев (пользователь нажмёт ещё раз).
- Принтер моно-лазерный (HP LaserJet 1102) — никаких цветовых опций.

### 7.3 Эндпоинт и UI

`POST /jobs/<job_id>/print`, поле `artifact` — имя PDF-файла.

Сервер: печать включена (`CUPS_PRINTER` непуст) → `artifact` присутствует в
списке файлов манифеста этого джоба И оканчивается на `.pdf` (whitelist из
манифеста, не листинг ФС — правило §1.6) → `print_pdf` → flash с id задания
или ошибкой → redirect на страницу джоба.

UI: кнопка «Печать A4» рядом с каждой PDF-ссылкой. Если `CUPS_PRINTER` пуст —
кнопок нет вообще (сервер не рендерит), PDF-ссылки остаются.

`_refingered.gp` серверно не печатается (это GP-файл, не документ) — красивую
нотную печать пользователь делает из самого Guitar Pro.

### 7.4 Приёмка Фазы 4

- PDF каждого таба: A4, моношрифт, системы не разорваны между страницами,
  колонтитулы на месте (открой файл и посмотри глазами).
- `lpstat -h 192.168.20.64 -a` показывает очередь; тестовая печать одной
  страницы прошла (спроси у пользователя подтверждение, что лист вышел).
- При недоступном CUPS (выключи `CUPS_SERVER` на несуществующий IP) — WARN
  на странице, джоб и файлы живы.

## 8. Тесты (`test_playable_tabs.py`)

Обязательные:

1. **Лиги:** синтетический трек (собрать GPSong-структуры руками) —
   залигованная нота даёт ОДНУ атаку с суммарной длительностью.
2. **Чистота score-MIDI:** в выходном .mid нет событий кроме
   note_on/note_off/set_tempo/time_signature/track_name/end_of_track.
3. **Маппер:** для простой хроматической фразы все лады ≤ max_fret, струн
   6 (гитара) / 4 (бас), `fret >= 0`.
4. **Fail-safe:** если tuttut кидает исключение (замокай), пайплайн
   возвращает результат с WARN, а gtrsnipe-файл создан.
5. **Питч-инвариант re-fingering (5.2)** как юнит: `new_fret` формула +
   реконструкция питча == исходный питч для всех нот фикстуры.
6. **Байт-идентичность при выключенной опции:** прогон `create_job` без флага
   до и после твоих правок даёт одинаковый набор и содержимое файлов
   (в тесте — хотя бы одинаковый список имён + размеров).
7. **Валидация regen:** запрос с `sweet_spot_high <= sweet_spot_low`,
   значением вне диапазона и с неизвестным полем → 400, mtime артефактов не
   изменился.
8. **PDF:** из синтетического ASCII-таба (3 системы по 6 строк, одна строка
   длиной 200 символов) создаётся файл с заголовком `%PDF`, размер страницы
   A4 (проверь метаданные), функция не упала на длинной строке.
9. **Печать:** `print_pdf` с замоканным `subprocess.run` — собирает верные
   аргументы `lp`; при `returncode != 0` возвращает ошибку, не исключение.
   Эндпоинт `/print` с именем файла не из манифеста → 400.

Фикстуры: `.gp`-файлы в git игнорируются (`.gitignore`), поэтому реальный
образец в тестах используй условно: `pytest.mark.skipif(not SAMPLE.exists())`,
где `SAMPLE = data/sessions/680ce724.../uploads/e1f2fae69d3b/input/
The_Princess_and_The_Dragon_copy.gp` (локально у пользователя он есть).
Синтетические тесты от файла зависеть не должны.
